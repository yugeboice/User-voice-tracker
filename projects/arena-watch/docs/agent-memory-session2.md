## 第 3 页｜Session 1 回顾：我们已经实现了什么？

### ✅ Session 1 的成果：Read-Only Memory（只读记忆）

在 Session 1 中，我们实现了**固定注入 JSON**（Hard Memory）：

**📁 核心文件**：
- `user_profile.json` - 存储用户偏好
- `UserProfile.cs` - 类型安全的数据模型
- `MemoryService.cs` - 加载记忆并构建 System Prompt

## 第 4 页｜记忆的 Schema 设计

设计记忆存储时，需要根据记忆类型、应用场景以及工程需求来定义字段。

### 1️⃣ 必需字段（基础字段）

无论是哪种记忆系统，都需要这些通用字段来标识和管理记忆：

| 字段 | 作用 | 示例 |
|------|------|------|
| `user_id` | 标识记忆属于哪个用户（多用户系统必需，单用户可忽略） | `"user123"` |
| `timestamp` | 记录创建/更新时间，用于生命周期管理和过期处理 | `"2026-01-12T14:30:00"` |
| `memory_type` | 标识记忆类型，帮助系统理解其重要性和持久性 | `"preference"` / `"fact"` / `"instruction"` |
| `content` | 记忆的核心内容 | `"用户是产品经理"` |

> 💡 **关于 memory_type**：
> 
> 记忆类型没有统一标准，可根据产品场景定义：
> - **按用途**：`preference`（偏好）、`fact`（事实）、`instruction`（指令）
> - **按心理学**：`episodic`（情景记忆）、`semantic`（语义记忆）、`procedural`（程序性记忆）

### 2️⃣ 可选字段（增强字段）

根据需求选择性添加：

**context（上下文信息）**

存储记忆产生时的上下文，支持软式注入（Conditional Memory）——只在特定场景下注入相关记忆。

```json
{
  "content": "用户关注推理能力的变化",
  "context": "GPT analysis",
  "memory_type": "preference"
}
```

**confidence（置信度）**

作用：表示 LLM 对该记忆重要性的置信度评分，范围通常是 0 到 1。这个字段可以帮助系统决定是否保存该记忆，或者在检索时优先考虑高置信度的记忆。

```json
{ "content": "用户偏好 TypeScript", "confidence": 0.85 }
```

**metadata（附加元数据）**

作用：根据工程需求存储额外的信息，诸如会话 ID、交互方式（语音/文字）等。

```json
{ "session_id": "abc123", "channel": "voice", "source": "explicit" }
```

**decay_info（时间衰减字段）**

作用：有些记忆可能随着时间的推移变得不那么重要，系统可以根据这些字段来决定是否需要删除或降级这些记忆。

```json
{ "created_at": "2026-01-12T14:30:00", "last_accessed": "2026-01-15T10:00:00" }
```

### 3️⃣ 我们的示例实现

在本教程的示例代码中，我们采用简化的 Schema：

```json
{
  "id": "mem_20260114143025",
  "content": "用户是产品经理，负责AI产品线",
  "category": "identity",
  "timestamp": "2026-01-14T14:30:25"
}
```

> 💡 **设计原则**：先用最小可行的字段跑通流程，再根据实际需求逐步扩展。

## 第 5 页｜记忆写入时机与管理

### 1️⃣ 记忆写入的条件

```json
{
  "trigger_condition": {
    "user_action": "new input / new preference",
    "task_status": "completed / updated",
    "pattern_recognition": "new habit detected",
    "system_event": "schedule change / notification"
  }
}
```

| 触发条件 | 说明 |
|---------|------|
| **User Action** | 用户新输入、修改了偏好或添加了新的任务信息 |
| **Task Status** | 任务从"未完成"变为"已完成"时，更新记忆 |
| **Pattern Recognition** | 识别到用户的新行为模式，自动记录 |
| **System Event** | 外部系统的变动（如日程提醒）触发记忆更新 |

### 2️⃣ 如何触发记忆更新

**直接触发**

用户输入或系统状态更新直接引发写入记忆。

> 示例：用户更新了面试时间或添加了新的任务。

**延迟触发**

系统通过对过去行为的周期性分析，自动触发记忆写入。

> 示例：系统识别到用户重复查看某个产品页面，便更新为"用户对这个产品感兴趣"。

### 3️⃣ 动态调整触发策略

为了避免频繁的写入导致系统负担或存储浪费，系统可以设计条件筛选：

- **设置阈值**：比如在 10 次对话后才记录用户的新习惯
- **存储限制**：内存限制，可以采用定期检查的方式，只保留最新的若干条记忆

### 4️⃣ 记忆写入后的管理策略

**定期评估**

每隔一段时间，系统对所有记忆数据进行有效性检查，评估是否有记忆已经过时，是否需要删除/修改。

**优先级设置**

根据信息的重要性或使用频率，对记忆进行分类（例如高优先级、低优先级），并设置不同的过期策略。

**自适应学习**

系统可以根据用户行为调整记忆更新的策略：

- 用户开始多次询问某个问题 → 系统认为该问题更重要，可以加入长期记忆
- 用户不再提及某个话题 → 系统删除不再需要的记忆

## 第 6 页｜如何利用记忆提升回复质量

我们在上一次课已经讲过固定注入 JSON（Hard Memory）的作用，这里补充说明如何利用条件注入的记忆来提升对话质量。

### 条件注入记忆（Conditional Memory）

一种简单的实现方式是直接让 LLM 来判断"要不要用哪些记忆"。

**一次典型流程**

```
用户输入
    ↓
LLM 判断当前任务类型
    ↓
选出相关记忆
    ↓
拼进 system / context
    ↓
生成最终回复
```

**可以直接给 coding agent 的指令示例**

```
在回复用户之前，先让 LLM 判断：

1. 当前用户输入属于什么任务类型
2. 哪些已存在的记忆对这个任务有帮助
3. 只把这些记忆拼进 prompt 再生成回复
```

**一个条件注入的示例 prompt**

```
【Task Type】
这是一个「教学设计」类问题

【Relevant Memory】
- 用户正在做 vibe coding 教学
- 目标读者是非技术背景

【Instruction】
基于以上记忆回答用户问题
```

## 第 7 页｜Vibe Coding 实操指南

> 💡 **本页目的**：基于示例代码的实际实现，指导你在自己的项目中实现 Memory Write 功能。


### 我们的架构设计

```
用户发送消息到 /api/chat
    ↓
LlmExample.ChatAsync 被调用
    ↓
[1] 加载用户记忆（MemoryService）
    ↓
[2] 构建 System Prompt（注入已有记忆）
    ↓
[3] 调用 LLM 生成回复
    ↓
[4] 返回回复给用户 ← 优先保证用户体验
    ↓
[5] 快速过滤：消息太短或是问候语？ ──是──→ 结束
    │
   否
    ↓
[6] 调用 LLM 提取记忆（MemoryExtractionService）
    ↓
[7] 如果提取成功 → 保存到 memories.json
    ↓
[8] 前端显示 "💾 I remembered: ..."
```

---

### Step 1：定义记忆的数据结构

**目标**：让项目能够存储和读取"记忆"信息。
**问题**：动态添加的记忆应该包含哪些字段，存储在哪里？

**推荐方案**：
1. 上节课中已经实现的`preferences` 字段 → 和动态添加的记忆相互独立
2. 新建 `memories` 数组或单独的文件 → 专门用于存储动态记忆 

**对 AI 说**：
```
"我的项目中有一个用于存储用户偏好的 JSON 文件。
我需要扩展它来支持存储记忆，请帮我完成：

1. 每条记忆需要包含以下信息：
   - id: 唯一标识符（如 mem_20260112143025）
   - content: 记忆的文本内容
   - category: 分类（preference、fact 或 instruction）
   - timestamp: 创建时间

2. 在现有的用户偏好json文件中，添加一个可选的记忆列表字段。

3. 确保能正确保存和读取 JSON。

请查看我现有的代码风格，保持一致。"
```

---

### Step 2：实现记忆提取服务

**目标**：创建记忆提取服务，包含消息过滤 + LLM 判断 + 控制台调试输出。

**我们的实现思路**：

```
用户消息
    ↓
【快速过滤】消息太短（<5字符）？ ──是──→ 跳过，不调用 LLM
    │
   否
    ↓
【LLM 判断】构建 Prompt 让 LLM 判断是否需要记忆
    ↓
【解析返回】解析 JSON
    ↓
【控制台输出】打印 LLM 返回的原始内容，方便调试
    ↓
返回 MemoryItem 或 null
```

**对 AI 说**：
```
"我需要一个记忆提取功能：

1. 先做快速过滤：
   - 消息太短（少于5个字）就跳过

2. 通过过滤的消息，让 LLM 判断是否值得记住：
   - 用户身份、偏好、兴趣 → 需要记住
   - 闲聊、问候、提问 → 不需要记住
   - LLM 返回 JSON 格式，包含判断结果和记忆内容

3. 在控制台打印 LLM 的返回，方便我调试

4. 解析返回结果，如果需要记住就返回记忆对象，否则返回空

5. 任何错误都不要崩溃，返回空就行"
```

**验收**：
- 运行后在控制台能看到 LLM 返回的内容
- 说"我是产品经理"能提取出记忆，说"你好"会跳过

---

### Step 3：实现记忆保存功能

**目标**：添加一个方法，将提取到的记忆保存到 JSON 文件。

**对 AI 说**：
```
"我需要把记忆保存到文件：

1. 读取现有的记忆文件（如果有的话）
2. 给新记忆生成一个唯一 ID
3. 把新记忆加到列表里
4. 保存回文件，中文要正常显示
5. 在控制台打印保存成功的日志

注意不要覆盖文件里原有的其他内容"
```

**验收**：调用后 JSON 文件新增 memories 数组，记忆内容正常显示

---

### Step 4：在对话中正确引用记忆

**目标**：在发送给 LLM 的请求中，把已保存的记忆注入到 System Prompt。

**我们的实现思路**：

```
用户发消息
    ↓
加载用户配置（user_profile.json）
    ↓
加载已保存的记忆（memories.json）
    ↓
构建 System Prompt，包含：
  - AI 助手的基本角色描述
  - 用户配置（名字、偏好语言等）
  - 已保存的记忆列表
    ↓
发送给 LLM：[System Prompt] + [用户消息]
    ↓
返回 LLM 回复
```

**System Prompt 的结构示例**：
```
You are a helpful AI assistant.

=== User Profile & Preferences ===
- Name: Alice
- Role: Product Manager
- Preferred Language: 中文
- Summary Style: 简洁

=== What I Remember About You ===
- [identity] 用户是产品经理，负责AI产品线
- [preference] 用户偏好TypeScript而非JavaScript
- [hobby] 用户喜欢爬山

Please adapt your responses according to the above context.
```

**对 AI 说**：
```
"我需要在对话时把已保存的记忆告诉 LLM。

修改构建提示词的地方：
1. 先加载用户配置（名字、偏好语言等）
2. 再加载所有已保存的记忆
3. 把这些信息拼成一段话，放在发给 LLM 的开头
4. 在控制台打印出来，方便我看到效果"
```

**验收**：
- 在控制台能看到发给 LLM 的完整提示词
- 提示词里包含之前保存的记忆
- AI 回复时能体现对记忆的理解

---

### Step 5：集成记忆提取到对话流程

**目标**：把记忆提取功能集成到主对话方法中，实现"边聊边记"。

**核心思路**：先返回回复给用户，再异步处理记忆提取，不影响对话体验。

```
用户发消息
    ↓
[Step 4] 加载记忆 → 构建 Prompt → 调用 LLM → 返回回复
    ↓
【返回回复给用户】← 优先保证用户体验
    ↓
[Step 2] 快速过滤：消息太短或是问候语？ ──是──→ 结束
    │
   否
    ↓
调用 MemoryExtractionService.ExtractMemoryAsync
    ↓
如果提取到记忆 → [Step 3] 保存到 JSON
    ↓
前端显示 "💾 I remembered: ..."
```

**对 AI 说**：
```
"把记忆提取集成到对话流程中：

1. 先正常回复用户（不要让用户等记忆处理）
2. 回复之后，检查用户消息是否需要记忆：
   - 太短或只是打招呼 → 跳过
   - 否则调用记忆提取
3. 如果提取到记忆，就保存
4. 每一步都在控制台打印日志
5. 记忆功能出错不能影响正常对话"
```

**验收**：
- 输入"我是产品经理" → 控制台显示 `[Memory Storage] ✓ Saved`
- 下次对话时，System Prompt 中包含新保存的记忆

```

**效果**：
```
[用户] 我是产品经理，负责 AI 产品线

[AI] 很高兴认识你！作为产品经理...

💾 I remembered: "用户是产品经理，负责AI产品线"
```

## 第 10 页｜优化思路与探索方向

> 💡 以下功能我们没有在上面做详细介绍，但在工程实践中常用。
> 作为进阶学习方向，供有兴趣的同学探索。

### 优化 1：记忆的条件注入：不把所有记忆都直接跟随system prompt注入，而是让 LLM 根据任务类型选择性注入相关记忆。
### 优化 2：记忆的生命周期管理：为不同类型的记忆设置不同的过期时间，定期清理过时记忆。
### 优化 3：记忆去重与记忆更新：用户多次提到同一信息，如何避免重复存储？用户的状态发生了改变，如何更新已有记忆？
### 优化 4：异步批量处理：将记忆写入操作异步化，减少对用户响应时间的影响。

## 附录｜真实案例：ChatGPT vs Claude 的记忆系统设计

> 💡 **学习目的**：通过逆向工程分析业界顶尖产品，了解两种不同的设计哲学。

### 📊 架构对比

| 维度 | **ChatGPT** | **Claude** |
|------|------------|-----------|
| **核心哲学** | 预计算 + 自动注入 | 按需检索 + 工具调用 |
| **记忆注入** | 每次对话自动注入 | 仅在 LLM 认为需要时检索 |
| **历史对话** | 预计算摘要（轻量） | 完整消息滚动窗口（详细） |
| **存储格式** | 离散事实列表 | XML 结构化文档 |
| **Context 预算** | 节省（用摘要） | 充足（~190k tokens） |

### 🔍 ChatGPT 的 4 层架构

**完整 Context 结构**：
```
[0] System Instructions（系统指令）
[1] Developer Instructions（开发者指令）
[2] Session Metadata（会话元数据 - 临时）
[3] User Memory（用户记忆 - 长期）  ← Memory Write 写入这里
[4] Recent Conversations Summary（近期对话摘要）
[5] Current Session Messages（当前会话消息）
[6] Your latest message（用户最新消息）
```

**关键设计**：
- **User Memory**：存储离散事实（如"用户叫张三""用户是产品经理"）
- **Recent Conversations**：只保存**用户的消息摘要**，不保存 AI 回复
  - 格式：`<时间戳>: <对话标题> |||| 用户消息片段 ||||`
- **提取时机**：对话结束后自动处理，用户无感知

**优势**：
- ✅ 速度快 - 预计算摘要，无需实时检索
- ✅ 成本低 - 摘要比完整历史省token

**劣势**：
- ❌ 丢失细节 - 摘要无法保留所有信息
- ❌ 固定注入 - 即使不相关也会注入

### 🔍 Claude 的工具调用架构

**完整 Context 结构**：
```xml
[0] System Prompt（系统提示词）
[1] <userMemories>
    - 用户叫 Manthan Gupta
    - 曾在 Merkle Science 工作
    - 偏好通过视频和论文学习
    </userMemories>
[2] Conversation History（对话历史 - 滚动窗口）
[3] Current Message（当前消息）
```

**工具系统**：
- `conversation_search` - 按主题/关键词搜索历史对话
- `recent_chats` - 检索最近的对话
- `memory_user_edits` - 处理用户的显式记忆管理命令

**关键设计**：
- **按需检索**：LLM 自己决定是否需要调用工具检索历史
- **完整消息**：保留完整对话，不做摘要
- **XML 格式**：结构化存储用户记忆

**优势**：
- ✅ 保留细节 - 完整对话历史可供检索
- ✅ 选择性注入 - 只在需要时检索相关内容

**劣势**：
- ❌ 非确定性 - LLM 可能"忘记"调用工具
- ❌ 多次调用 - 检索需要额外的 LLM 调用
