## 第 3 页｜为什么需要"人为"给 AI 实现记忆？

### 1️⃣ 没有 orchestration 的模型能记住什么？

**Transformer 架构的天然限制**：
- 只能"看到" context window 里的 token (你可以简单理解为"字"或"词")

> 💡 **通俗类比：金鱼记忆的超级教授**
> 
> 想象 AI 是一位博学多才的教授，但他只有 **"当前时刻"的记忆**（或者更准确地说，他只能看见**眼前黑板上**写着的东西）。
> 
> - **Transformer 的注意力机制（Attention）**：
>   这就好比教授戴着一副**只能看清黑板**的眼镜。他处理问题时，会疯狂地在黑板上的文字之间找关联（Attention）。
>   **比如黑板上写着"苹果"这个词，教授必须看整句话来决定怎么理解：**
>   - 句子 1：**"我咬了一口红色的苹果。"** -> 教授的目光（Attention）会聚焦在 **"咬"** 和 **"红色"** 上，从而理解这是 **水果**。
>   - 句子 2：**"苹果发布了新款 iPhone。"** -> 教授的目光会聚焦在 **"发布"** 和 **"iPhone"** 上，从而理解这是 **科技公司**。
> 
> - **天然限制**：
>   如果黑板（Context Window）擦掉了，或者写满了把最早的内容挤出去了，教授就**彻底断片**了。他不知道你是谁，也不知道刚才聊了什么。
> 
> - **为什么需要"人为"设计记忆？**
>   因为教授自己**没有大脑皮层来存长期记忆**。
>   我们需要做一个 **"小抄系统"** ：每次请教教授之前，先把必须要记住的关键信息（比如"我是张三，我住在北京"），**重新抄一遍**写在黑板的最上面。
>   这样，教授一抬头（Attention 扫描），就能看到这些信息，仿佛他一直记得一样。

**具体例子：当前主流模型的 Context Window**

| 模型 / 版本 | 上下文窗口规模 | 能"记住"多少？ | 主要适用场景 |
| --------- | ------------ | ------------ | ---------- |
| **GPT-3（2020）** | 2,048 tokens | 约 1500–1600 个英文单词<br>约 1200–1800 个中文字 | ❌ 几乎什么都记不住 |
| **GPT-5 API** | ~1,000,000 tokens | 约 750K 英文单词<br>约 600K–900K 中文字 | 超长对话、长文档、Agent 工具链 |
| **GPT-5 Plus/Pro** | ~32K / 128–196K tokens | 约 24K / 96K–147K 英文单词 | 普通应用交互与中等对话 |
| **Google Gemini 3 Pro** | ~1,000,000 tokens | 约 750K 英文单词 | 多模态大规模上下文场景 |
| **Claude 系列** | ~200K tokens | 约 150K 英文单词 | 中大上下文任务 |

**💡 如果有一天 context window 非常大，还需要记忆系统吗？**

**外部记忆的优势**：
- ✅ 明确标记 + 固定位置（prompt 开头）
- ✅ 结构化（JSON）让模型清楚"这是需要遵守的设定"

### 3️⃣ 控制性问题
- 控制 AI "记住"什么
- 让用户能删除/修改记忆
- 让不同任务使用不同记忆

**对比**：
| 维度 | 全部放 context | 记忆系统 |
|------|---------------|---------|
| 成本 | $100/次 | $0.01/次 |
| 效果 | 偏好可能被忽略 | 清晰可见 |
| 控制 | 无法编辑 | 可随时修改 |

**我们的解决方案：记忆系统**
- 把需要AI"记忆"的东西**持久化存储**在外部（数据库、文件等）
- 在用户和AI对话时，**选择性地**把关键信息注入 context window
- 这样 Transformer 在处理当前请求时，能够"看到"你要求AI"记住"的东西
- **关键优势**：只记住重要信息，成本低，可跨越长时间，不依赖 context window

> 🧠 **核心认知**：
> 
> **Agent 的"记忆能力"，**
> **不是 Transformer 模型的能力，**
> **而是 orchestration 设计能力。**

## 第 4 页｜Agent 记忆的三种类型

### 1️⃣ 固定注入 JSON（Hard Memory）
> 💡 **实例**：To B 的 Agent 需要在**每一次**对话中都能记住当前用户是哪个公司、什么岗位的，这样才能保证回答视角不出错。

**定义**
- 每次调用模型都会注入
- 相当于 prompt 的一部分

**Use Case**
- 用户稳定偏好
- 不随任务变化的背景信息

### 2️⃣ 软式注入 JSON（Conditional Memory）
> 💡 **实例**：
> 你设计了一个竞品分析 agent ，你已经定义了一些通用的分析维度。但是最近在分析**GPT**模型的更新时，你更想关注它**推理能力**的变化；在分析**Gemini**时，你更想关心它**图片生成**方面的能力。
> 如果你要求AI针对GPT给出分析结论，**你关心Gemini的图片生成能力**这个信息就不会被加载，从而节省 Token 成本并减少干扰。

**定义**
- 在特定任务 / 条件下才注入
- 由 agent 在生成前判断

**Use Case**
- 不同任务不同风格
- 财报 vs 新闻 vs 舆情

### 3️⃣ 向量库（Vector Memory）
> 💡 **工程实例：ChatGPT 的 Memory 功能**
> 比如和ChatGPT讨论旅游计划后，ChatGPT保存了这些记忆：
> - "用户将在10月3日从北京出发去哥本哈根..."
> - "用户喜欢自然风光，但希望公共交通便利..."
> 这些是非结构化的文本。当你下次问 "帮我做旅游攻略" 时，系统通过 **语义搜索 (Semantic Search)** 发现这些话跟当前任务**相似度很高**，就会自动把它们捞出来给模型看。

**定义**
- 存自然语言经验
- 在"相似情境"下被召回

**Use Case**
- 用户对 AI 行为的反馈
- 难以结构化的偏好

## 第 6 页｜固定注入 JSON：具体例子

### 示例：AI公司新闻总结 Agent

```json
{
  "user_profile": {
    "region": "China",
    "focus_companies": ["OpenAI", "Google","Anthropic","ByteDance"],
    "summary_style": "concise",
    "tone": "neutral"
  }
}
```

**实际注入到 prompt**：
```
用户偏好：
- 地区关注：China
- 语言：中文  
- 重点公司：OpenAI、Google、Anthropic、ByteDance
- 格式：要点列表
- 长度：200字以内
- 语调：客观中性

请根据以上偏好总结这条新闻：[新闻内容]
```

## 第 7 页｜固定 JSON vs System Prompt：Vibe Coding 视角的选择

### 💡 常见问题：它们有什么区别？

| 维度 | System Prompt (The "Soul") | 固定注入 JSON (The "Config") |
| :--- | :--- | :--- |
| **作用范围** | 决定 Agent 的**底层逻辑** | 决定 Agent 的**当前状态** |
| **内容性质** | 规则、指令 (Instructions) | 数据、变量 (Data) |
| **修改频率** | 低（写完很少改动） | 高（随需求/场景变化） |
| **维护方式** | 修改代码 / Prompt 模板 | 修改 JSON 文件 / 数据库 |
| **表现形式** | 自然语言段落 | 结构化 Key-Value |

### 示例对比

```csharp
// System Prompt（逻辑层：怎么处理数据）
// 这里的逻辑通常写好后很久都不动
var systemPrompt = """
You are a stock analyzer. 
Analyze the companies in the user's portfolio.
Output format: Markdown table with 'Price', 'PE Ratio', 'Recommendation'.
"""

# 固定注入 JSON（数据层：处理什么数据）
# 这里的内容可能跟随用户需求经常变动，适合放在外部 JSON 文件里方便修改
user_context = {
  "portfolio": ["AAPL", "MSFT", "TSLA", "NVDA"],
  "risk_tolerance": "high",
  "investment_horizon": "long-term"
}
```

### Vibe Coding 决策树

1.  **这是"规则"还是"数据"？**
    *   "不要使用表情符号" -> 规则 -> **System Prompt**
    *   "我的名字叫 Alice" -> 数据 -> **JSON**

2.  **这是一个"列表"吗？**
    *   如果有一长串东西（比如 10 个关注的股票代码），放 System Prompt 会很乱 -> **JSON**

3.  **你想能够灵活地调整这段内容吗？**
    *   如果希望对这段内容能够灵活调整，比如随时增删竞品分析中关注的公司 -> **JSON**

## 第 8 页｜固定注入 JSON 的 Vibe Coding 实操

### 1️⃣ 第一步：设计你的 JSON 模板 (Schema)
在开始写代码之前，先定义好你的 Agent 需要记住哪些字段。这就像是给数据库建表。

**模板示例**：
```json
{
  "basic_info": {
    "name": "",         // 待填
    "role": ""          // 待填
  },
  "preferences": {
    "language": "中文", // 默认值
    "style": ""         // 待填
  }
}
```

> 💡 **Vibe Coding 技巧**：先写好这个 JSON 结构，后面让 AI 帮你写代码时，直接把这个结构发给它，它就能自动生成对应的提取和注入逻辑。
> **为什么要先设计模板？**
> 1. **明确需求**：强迫自己想清楚产品需求，到底要 Agent 记住什么。
> 2. **减少幻觉**：明确的字段定义能让 LLM 提取时更精准，不会瞎编字段。

> 🛠️ **实操：如何让 Coding Agent 帮你设计这个 Schema？**
> 你可以直接对 Coding Agent 说：
> "我正在做一个[你的Agent功能，比如：竞品分析助手] Agent。请帮我设计一个 UserProfile 的 JSON 结构，用来存储用户的长期偏好（比如[举例：关注的竞品名单、报告的语言风格]）。请给出 JSON 示例。"


### ❓ 我们的示例代码里，有个 user_profile.json , 还有个 UserProfile.cs ，区别是？

**其实只用 JSON 也可以，但加上 C# 类是为了"防呆"（更稳定）。**

**通俗类比：Excel 的表头与数据验证**
- **JSON** 是你填写的**内容**。
- **C# 类** 是你设置的**表头和规则**。

**它的作用**：
如果不定义 C# 类，代码也能读 JSON（弱类型读取），但如果 JSON 里把 `name` 拼成了 `nmae`，程序可能就默默地崩了，或者把错误的信息发给了 AI。
有了 C# 类，程序就能**严格检查**你的 JSON 格式对不对。如果格式不对，它会立刻报错，而不是让错误溜进 Prompt 里。

> **结论**：C# 类不是必须的，但它是让 Agent **稳定运行的保险丝**。你可以不关注 `.cs`文件的内容，完全交给coding agent来管理。

### 2️⃣ 第二步：注入记忆 (Injection)

**原理非常简单：字符串拼接**

我们不需要复杂的代码，只需要把 JSON 里的内容读出来，转换成文本，然后**硬塞 (Concatenate)** 到 System Prompt 的后面即可。

> 💡 **直观演示**
>
> 我们的示例代码打印了最终发给 LLM 的 Prompt 结构，你会看到：
> 1.  最上面是 System Prompt（"你是一个助手..."）
> 2.  中间是我们注入的 **User Profile**
> 3.  最后是用户的提问

1. **设计 (Design)**：

3. **验证 (Verify)**：
   - 手动修改 `user_profile.json` 文件（例如把语言改为 "English"）。
   - 运行 Agent，观察终端输出的 Prompt 是否包含了你的修改。
   - 和 Agent 对话，看它是否真的听从了你的设定。
